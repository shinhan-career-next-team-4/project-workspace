## 항목별 의견

- [C12a-0 원칙] 수정 — 원칙 1의 "프론트가 하는 일" 목록이 (d) 만원↔원 하나뿐인데, 실제로는 (e) 'n년 n개월'↔개월(곱셈·나눗셈), (f) 422 `min`·`max`를 입력칸 단위 문구로 바꾸기도 한다. 이 둘이 명시되지 않으면 화면마다 제각각 만들어 CP-04 위반이 된다. 수정안: 허용 목록에 (e)(f)를 넣고, 변환 규칙을 한 곳(프론트 util 1개 + 단위 테스트)에 둔다고 적는다. 규칙은 R-3 참고.

- [C12a-1 엔드포인트] 수용 — `/me` 없이 P-4 하나로 401/409/200이 갈리는 것은 좋다. 단 목에서 시작 상태가 문제다(C12a-12 참고).

- [C12a-2 쿠키·401·`code` 분기] 수용 — R-2 찬성. 래퍼 규칙을 한 줄 더한다. (1) 본문이 `application/problem+json`이 아니거나 파싱에 실패하면(프록시 502, HTML) `code=undefined`로 보고 네트워크 오류 경로로 보낸다. 로그인 화면으로 보내지 않는다. (2) `UNAUTHENTICATED`를 받으면 공유 상태·폴링을 모두 비운다(C12a-11-2 로그아웃과 같은 정리). P-3에서 401이 나면 입력값은 잃는다. 데모 범위에서 수용한다.

- [C12a-3 로그인] 수용 — `{}` 본문과 "성공 뒤 P-4로 분기"도 좋다. 단 J-12a가 분기를 #47 담당으로 적었는데 실제 Issue는 다르다(R-11 참고).

- [C12a-4 로그아웃] 수용 — 오류별 동작이 기계적으로 고를 수 있다.

- [C12a-5 P-3 입력 저장] 수정 — 다섯 가지.
  1. **goalType 목록이 계약에 없다.** 입력 화면 드롭다운을 만들려면 코드 목록이 있어야 한다(`#19 enum 확정`으로 미뤄져 있음). 수정안: 계약 본문에 임시 목록을 적고 문구표 `goal.<CODE>`와 같은 키로 맞춘다.
  2. **422 목이 모자란다.** `TOO_MANY_DECIMALS`(`scale` 포함)와 `NOT_INTEGER` 목이 없다. R-3(b)로 가면 소수 입력이 가능해져 이 둘이 실제로 나온다. `put-plan.422-decimals.json`을 추가한다(C12a-10에 `scale`이 있으나 예시에는 없다).
  3. **PLAN_CHANGED 뒤 재저장은 다른 탭의 변경을 말없이 덮어쓴다.** 의도된 동작이므로 수용한다. 다만 안내 문구에 "현재 계획이 바뀌었어요. 다시 저장하면 입력한 값으로 바뀌어요" 취지를 넣는다(문구표 `plan.changedElsewhere`).
  4. **입력 화면에 비중 칸이 없고 서버가 비중을 복사 유지한다(R-9, 아래).** 사용자가 현재 비중을 알 수 있어야 한다. 수정안: 입력 수정 화면에 `display["conditions.savingsRatioPct"]`를 읽기 전용으로 보여 준다(문구표 한 줄).
  5. `targetPeriodMonths`는 년·월 두 칸으로 받아 `년*12+월`로 보낸다. 채울 때는 `÷12`, `%12`다. 이 규칙을 (e)로 명시한다.

- [C12a-5-4 오류 동작] 수용 — 500 뒤 P-4를 다시 부르는 흐름은 맞다. 422의 범위 문구는 하드코딩 금지·`min`/`max` 기준으로 하는 것에 찬성한다. 변환 규칙을 정한다. KRW는 `만원` 정수 + 천 단위 쉼표, "약" 없음(최소·최대는 만원 배수라 반올림이 없음). MONTH는 'n년 n개월'(360 → "30년"). PCT는 `N%`. CHAR는 `N자`.

- [C12a-6 PlanView] 수정 — 세 가지.
  1. **`calcRunId`가 같은 계획에서 바뀔 수 있다(반대).** C12a-5-2는 P-3의 계산과 `PlanChanged(INPUT)` 리스너가 같은 (버전, PLAN) 행을 2개 만들 수 있고 "무해"라고 했다. 그런데 P-4가 "최신 PLAN calc_run"을 돌려주면 P-3이 준 `calcRunId`(553)와 이후 P-4가 주는 값(554)이 달라진다. #54는 "`calcRunId`가 바뀌고 `CALCULATED`면 F-3"이므로 revision이 그대로인데 설명이 한 번 더 요청된다(계산 비용·중복 EXPLANATION). 수정안: 같은 (버전)에는 항상 같은 `calcRunId`를 준다(예: 가장 작은 id를 고정 선택), 또는 계약에 "F-3 호출 조건은 `revision` 변화 + `CALCULATED`"로 바꾼다. 앞쪽이 쉽다(조회 쿼리 한 줄).
  2. **`revision`과 `status`의 갱신 시점이 어긋난다(반대).** F-5·P-5는 `{revision}`만 준다. 프론트는 먼저 `revision`을 바꾸고 나중에 P-4로 `status`·`calcRunId`를 얻는다. D-072("`revision`이 바뀔 때마다 현재 초과 여부를 다시 판단")를 `revision` 구독 시점에 하면 이전 `status`로 판단한다(적용으로 초과가 풀리거나 생기는 경우). C12a-6-5는 "한 번에 바꾼다"고만 적혀 있다. 수정안: 공유 상태를 두 칸으로 나눈다. `revision`(모든 쓰기 응답이 갱신, D-069 버튼 비활성의 구독 대상)과 `view`(`PlanView`로만 갱신되는 {revision, calcRunId, status}, D-072 판단과 #54 F-3이 구독). 이 규칙을 계약에 쓰고 #49·#51·#53·#54 본문에 반영한다.
  3. **응답 순서 역전 방지.** P-4가 느린 응답으로 뒤늦게 도착해 큰 revision을 작은 revision으로 덮을 수 있다. 수정안: `view`는 도착한 `revision`이 현재 값 이상일 때만 교체한다(로그아웃·`NO_PLAN`으로 `null`이 된 뒤는 예외).

- [C12a-6-2 monthlyPoints] 수정 — 시작·끝 점이 정해지지 않았다. 목 규칙은 첫 점이 `2026-12`인데 가로축 왼쪽 라벨은 `display.calcStartMonth`("2026년 11월")라 어긋난다. 엔진(#27) 정의에 맡기면 프론트가 축 라벨을 다시 만들게 된다. 수정안: 계약에 "마지막 점의 `month` = `result.targetMonth`, 첫 점의 `month` = `result.calcStartMonth`(원금 = 보유 자산)"를 고정하고 #27 테스트로 둔다. 목은 k=0 점을 더해 37점으로 맞춘다.

## R 의견

- **R-1 (새 목표 세우기)**: 수용. 별도 동작 없이 P-3 하나. 화면 문구에서 "새 목표 세우기"와 "입력 수정"을 같은 화면·같은 버튼으로 둔다.
- **R-2 (401 `INVALID_CREDENTIALS` + `code` 분기)**: 찬성. 400/422로 두면 입력 검증 오류와 섞여 오히려 복잡하다. 래퍼 규칙은 위의 두 줄 추가(비JSON 본문 처리, 401 때 상태 정리).
- **R-3 (입력 단위)**: 안 (b) 변형을 권장한다. 만원 칸에 **소수를 허용하되 십진 문자열 이동으로만 변환**한다(부동소수 곱셈 금지: `1.1*10000`은 `11000.000000000002`). 345,000원 → "34.5", 123,456원 → "12.3456", 정수 만원은 "30". 소수는 4자리까지, 초과하면 프론트가 막고 서버가 `NOT_INTEGER`로 받는다. 반올림·내림이 없어 값이 손실되지 않고 "저장하면 값이 바뀌어요" 안내(안 c)도 필요 없다. (a) 원 단위 칸은 CP-02(만원 단위)와 충돌하고, (c) 내림은 저장 시 조용히 값이 바뀌어 AI 숫자와 어긋난다. 근본 대안은 `rules.yml`에 금액 키 `step: 10000`을 두고 대화·대안·입력 모두 같은 검증을 거치게 하는 것이지만, 대화 값 되묻기 범위가 늘고 #17·B팀 영향이 있어 질문(Q)으로 올릴 일이다. 이번 계약에서는 (b)로 닫고 Q로는 올리지 않아도 된다. 변환 util과 단위 테스트(`34.5 ↔ 345000`, `0.0001 ↔ 1`)를 #48에 둔다.
- **R-4 (범위 임시값)**: 제공자 영역. 소비자 영향은 422 `min`·`max`를 그대로 읽으므로 없다. 값이 바뀌어도 목만 갱신하면 된다.
- **R-5 (그래프 숫자)**: **툴팁·세로축 눈금 숫자에는 서버 문자열이 필요하다.** 프론트가 눈금 값을 `result` raw로 계산·포맷하면 "프론트는 숫자를 만들지 않는다"와 CP-04(1만원 미만·1억 이상 규칙)가 깨진다. 선택지 둘. (A) 숫자를 아예 보이지 않는다: 목표선 라벨(`display.goalAmount`)과 가로축 양 끝(`display.calcStartMonth`·`targetMonth`)만 쓴다. 비용 0이다. (B) `monthlyPoints[].afterTaxAssetDisplay`를 더한다: 36점 × 3시나리오 약 100개 문자열, 빌더 한 줄. **데모 범위에서는 (A)로 수용한다**(FR-RES-04는 "과정을 목표선과 함께 보여준다"뿐이고 점별 금액은 요구하지 않는다). 단 세로축 눈금 숫자와 툴팁을 넣지 않기로 #50에 명시한다. 월 라벨은 `"YYYY-MM"`을 그대로 보이거나 표시하지 않는다. 시나리오 최종값 라벨은 마지막 점이 아니라 `display["S.afterTaxAsset"]`를 쓴다.
- **R-6 (Secure 쿠키)**: 제공자 영역. 프론트는 Vite 프록시를 쓰므로 `localhost` http에서는 대개 문제가 없다. 막히면 `auth.cookie.secure=false`면 충분하다.

## 소비자 쪽에서 꼭 필요한 것

1. **목 시퀀스 기본 파일**(C12a-12 수정안). 이것 없이는 "로그인 → 입력 → 결과 → 수정 → 되돌리기 → 로그아웃"을 목만으로 만들 수 없다.
2. **같은 계획 버전에는 항상 같은 `calcRunId`**를 준다(또는 F-3 조건을 `revision` 기준으로 바꾼다). 없으면 #54가 F-3을 중복 호출한다.
3. **공유 상태 두 칸 규칙(`revision` / `view`)과 역전 방지.** 없으면 D-072 초과 판정이 적용·되돌리기 직후 틀린 `status`로 나간다.
4. **그래프 점의 시작·끝 월 고정**(첫 점 = `calcStartMonth`, 마지막 점 = `targetMonth`). 없으면 축 라벨이 어긋난다.
5. **goalType 코드 목록**을 계약 본문에 임시로라도 적는다(#48 드롭다운).
6. **단위 변환·범위 문구 규칙**(만원 소수 이동, n년 n개월, 422 문구)을 계약에 적고 util 하나로 둔다.
7. `display` 키 표기를 `display["…"]`로 통일, `scenarios[]` 순서 규칙.
