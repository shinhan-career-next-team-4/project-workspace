# 소비자 재검토(4단계): frontend-api-plan-v4 (#12-a 개정, `savingsRatioPct` 요청 필드)

검토자: contract-consumer(프론트 입력·결과 #48·#49·#51, B팀 대화·대안·비교 #52~#54·#64·#66 입장). 대상: `frontend-api-plan-v4.md`. 대조: `review-frontapi-plan-v4-consumer.md`(내 1차), `review-frontapi-plan-v4-provider.md`(제공자 1차), `frontend-api-plan.md`(v3 최종본, `expectedRevision` 200·226·235행), `decisions.md`(D-043·085).

판정: 수정하면 수용 (두 줄 보강하면 닫힌다. Q로 올릴 쟁점은 없다)

**쟁점 Z-1 답: A (기획안, 되보내기) 수용.** 조건 둘: (1) (h) 표의 세 번째 행을 "ON + 칸 비움 → **저장 시점의 `plan.savingsRatioPct`, 값이 없으면 `null`**" 한 규칙으로 통일한다. (2) 로딩 전에는 저장을 막는다(아래 1번).

## 항목별 의견

### 1. 쟁점 Z-1: 되보내기 (요점 1)

- **[내가 지적한 "일반 수정이 대화 비중을 지운다"] 해소됨 — 수용.** 복원 ON(`plan.savingsRatioPct !== null`)이 기본 상태이고 칸을 비운 일반 수정(목표 금액만 고침)은 받은 값을 그대로 돌려보내므로 대화·대안 비중이 유지된다. "끄면 5:5"도 OFF가 언제나 `null`이라 참이다. 내 ③안(`50`)이 프론트에 기본 비중 수치를 복제한다는 제공자 (B) 반대에 동의한다. ③안은 철회한다.
- **[구멍 1: 응답을 못 받은 상태·`loadPlan()` 전 저장] 수정 — 실제로 걸리는 유일한 구멍.** 로딩 전에는 토글 초기 상태를 모르므로 기본 OFF로 보이고, 이때 저장하면 `null`이 가서 **서버 비중이 지워진다**(되보낼 값이 아직 없을 뿐인데 OFF와 구분되지 않는다). 수정안: 입력 화면은 `loadPlan()`이 끝나 `plan` 칸이 `확정(있음/NO_PLAN)`이 되기 전에는 폼과 저장 버튼을 비활성으로 둔다(#47 가드와 같은 방식). GET 실패(네트워크 오류)일 때도 저장을 막고 다시 시도 안내를 보인다. 되보낼 값은 **폼 로컬 state에 복사해 두지 말고 저장 누르는 시점의 공유 상태(`plan`)에서 읽는다**(대화 적용·undo로 `revision`이 바뀌면 같이 갱신되므로). 이 한 줄을 (h)에 적는다.
- **[구멍 2: 되보낼 값이 낡은 경우] 새 구멍 아님 — 수용.** 다른 탭·대화에서 비중이 바뀌었으면 요청의 `expectedRevision`이 달라 `409 PLAN_CHANGED`(최종본 226·235행, 입력 수정에도 검사)로 막히고, 되보낸 옛 값이 새 값을 덮지 못한다. 이 사실을 (h)에 한 줄 적으면 B팀이 의심하지 않는다.
- **[구멍 3: 되보낼 값이 없는 경우] 수정(문장 정리).** 토글 ON·칸 비움인데 `plan`이 `NO_PLAN`이거나 `savingsRatioPct`가 `null`이면 되보낼 값이 없다. 이때 보낼 값은 `null`(= 5:5)이며 결과는 "칸 비움 = 기본 비중"으로 일관된다. v4 (h) 표는 "복원 ON"이라고만 써서 사용자가 OFF에서 다시 ON으로 켠 경우와 첫 입력 ON·칸 비움이 표에 없다. 수정안: 세 번째 행을 "ON + 칸 비움 → `plan.savingsRatioPct ?? null`"로 쓰고, 단위 테스트(#48)에 두 경우를 더한다. ① 첫 입력·ON·칸 비움 → `null` ② 복원 OFF→ON·칸 비움(비중 83) → `83`. 또 `undefined`가 JSON에서 키를 지우므로 요청 본문 생성부는 항상 `?? null`로 키를 채운다는 테스트 한 줄(Z-17 키 필수가 깨지면 `422 REQUIRED`).
- **[그 밖의 확인] 이견 없음.** OFF 상태에서 칸이 채워져 있어도 `null`을 보낸다(칸은 비활성 또는 숨김, 아래 K-3). 합 0(두 칸 "0" 입력 포함)은 칸 비움으로 취급해 비중이 유지될 수 있다. 사용자가 저축 0원을 의도한 경우로서 해가 없어 수용한다.
- **[ratioKept 도움말 조건] 수정(작음).** `input.ratioKept`("현재 비중을 그대로 써요")는 **칸이 비었고 토글 ON일 때** 보인다. 첫 입력에서도 "현재 비중 = 기본 비중"이라 거짓은 아니다. 표시 조건을 "복원일 때만"이 아니라 이렇게 적는다.

### 2. NFR-INT-01 (요점 2)

수용. 되보내기는 받은 정수를 변환·연산 없이 돌려주는 것이라 계산이 아니다. 산출은 (g) util 한 함수뿐이고 D-087 예외 한 줄이 이미 있다. 조건: 되보낼 때 `Number()`·반올림 같은 가공을 하지 않는다(단위 테스트가 "응답 83 → 요청 83"을 고정).

### 3. 안내 문구: `input.ratioResetNote` 대신 `input.existingSavingHelp` (요점 3)

수정하면 수용, **별도 키는 불필요**. 이유: 토글 설명은 상시 노출 문장이라 사용자가 끄기 전에 읽을 수 있고, 키가 하나 줄어 문구표·#18 변경이 작다. 두 조건:
1. 문장은 토글 바로 아래에 **항상 보이게** 둔다(툴팁·접힘 금지). 끌 때만 알려 줄 필요는 없지만 접히면 안내가 사라진다.
2. 문장에 **"5:5"·"적금 5 : ETF 5" 같은 수치를 쓰지 않는다**("끄면 기본 비중으로 돌아가요"). 제공자가 기본 비중 `50` 복제를 CP-02로 반대한 것과 같은 논리다. 문구표에 수치를 박으면 기준 데이터 파라미터가 바뀔 때 문구만 거짓이 된다. 사용자가 실제 비중을 확인하는 곳은 결과 화면 조건 바(`display["conditions.savingsRatioPct"]`)다. 내 1차의 `ratioResetNote`("적금 5 : ETF 5")도 같은 이유로 철회한다.

### 4. v4 Z-6·Z-8·Z-11~Z-17, C12a-16 중 어긋나거나 빠진 줄 (요점 4)

- Z-6 일치(정수 HALF_UP·표 9행). Z-8 일치(고정 문장·`!== null` 조건. 대화로 정한 비중에서도 뜨지만 문장이 중립이라 해 없음). Z-11·Z-12·Z-13·Z-15·Z-16 일치. 어긋난 줄은 아래에 한정한다.
- **Z-14 / (g)**: 내 1차는 "한 칸만 비면 0, 두 칸 다 비면 칸 비움". v4 문장 "빈 칸은 0으로 보고, 합이 0이면 칸 비움"과 같다. 어긋남 없음.
- **Z-17**: 키 필수 반영은 맞으나 "되보낼 값이 `undefined`일 때 키가 빠진다"는 위험이 빠졌다. (h) 단위 테스트에 "`plan` 미로드·`savingsRatioPct` 없음이어도 본문에 `savingsRatioPct` 키가 있다"를 더한다(1번 구멍 3).
- **(h) 단위 테스트 줄(88행)**: 4경우만 있다. 복원 OFF→ON·칸 비움(`83`)과 응답값을 가공하지 않음(`83` → `83`)을 더해 6경우로.
- **Z-16/K-6**: "#18(없으면 #127 paths)"은 담당이 둘로 보인다. 어느 쪽인지 하나로 정한다. 키 수는 7개가 맞고 `input.ratioResetNote`는 없어야 한다(3번).
- **K-3**: "로딩 전 저장 비활성", "OFF에서 납입액 칸 비활성/숨김", "되보낼 값은 저장 시점의 공유 상태에서 읽음"이 빠졌다. 1번 구멍 1 때문에 수용 기준에 넣는다.
- **K-9**: "토글을 끈 입력 저장은 적용된 비중을 5:5로 되돌린다"를 후속으로 미뤘으나 B팀 영향은 거의 없다(서버 409가 같은 탭을 막고 D-069가 버튼을 끈다). 후속으로 둬도 무방하다. 다만 #127 문구 정정과 같이 한 줄 적자.
- C12a-16의 K-1·K-2·K-4·K-5·K-7·K-8은 내 1차와 맞는다.

### 5. 제공자 검토에서 소비자에게 영향 있는 것 (요점 5)

- **422 `unit.pct` 오표시**: 동의. `field: savingsRatioPct`일 때 `unit.ratioPct`로 가른다(v4 Z-9·(f)). 화면이 0~100만 만들어 이 422는 거의 안 나므로 단위 테스트 한 줄이면 충분하다.
- **차액 문구는 서버 `display`에 없음**: 동의. 서버는 납입액을 받지 않는다(D-043). 고정 문장을 프론트 문구표로 둔다.
- **목은 응답 전용**: 동의. 요청 본문은 단위 테스트로 본다. 제공자가 권한 `put-plan.422-ratio-range.json`은 필요 없고, 제공자도 "양보 가능"으로 적었다.
- 이견 없음. 제공자가 확인한 `PlanService`의 시작월만 복사·비중은 요청 값(Z-4)도 소비자에게 영향이 없다.

## 소비자 쪽에서 꼭 필요한 것
1. `loadPlan()` 확정 전에는 입력 저장 불가(1번 구멍 1). 없으면 대화 비중이 조용히 `null`로 지워진다.
2. (h) 세 번째 행을 `plan.savingsRatioPct ?? null` 한 규칙으로 통일하고 키는 항상 채운다(구멍 3).
3. `existingSavingHelp`는 상시 노출, 수치 없는 문장(3번).
