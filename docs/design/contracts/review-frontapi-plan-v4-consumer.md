## 항목별 의견

### 1. 입력 화면 구현 가능성 (요점 1)

- **[요청 필드 `savingsRatioPct`, 키 필수·`integer | null`] 수용** — 화면이 켠 토글만 값을 보내고 끈 상태는 `null`이라 분기가 단순하다(v4 초안 17~19행). 응답의 `plan.savingsRatioPct`는 이미 있어(목 `put-plan.200.json` 20행) 복원에도 쓴다. 단 "키 필수"이므로 지금 #48이 만든 요청 본문(키 없음)과 목 요청 예시·계약 C12a-5-1 본문 예시(342행 근처)에 `"savingsRatioPct": null`을 모두 더해야 한다. 안 더하면 `REQUIRED` 422가 난다.
- **[산출식이 NFR-INT-01에 걸리지 않는다는 주장] 수정하면 수용** — NFR-INT-01은 "금융 계산은 Spring 계산 엔진에서만"(`srs.md:78`)이고 "금액"만으로 한정하지 않는다. 비율 나눗셈이 면제라는 말은 초안의 자체 해석이다. D-084는 같은 종류의 화면 계산에 "NFR-INT-01의 예외"라고 명시했는데 D-085에는 그 문장이 없다(`decisions.md:90·91`). 수정안: ① D-085(또는 FR-INP-08 비고)에 "비중 산출은 입력 보조 계산으로 NFR-INT-01 예외, 저장·계산·결과는 서버 값"이라고 D-084와 같은 모양으로 적는다. ② 이 계산은 **util 한 함수**(C12a-5-6 (d)(e) 옆, 공용 폴더)로만 하고 금액·차액 계산은 절대 하지 않는다고 못 박는다. 대안(두 납입액을 일회용 필드로 서버에 보내 서버가 산출)은 계약·DB·검증이 늘고 D-043 문장과 어긋나 비추천이다.
- **[반올림 `.5` 규칙] 반대(미정의) → 수정안** — "반올림"만 있으면 프론트(JS `Math.round`)와 테스트 작성자가 부동소수로 `a/(a+b)*100`을 계산해 12.5·62.5류에서 갈릴 수 있다. 수정안: **정수 연산, 0.5는 올림(HALF_UP)**: 두 납입액을 (d)로 원 정수로 바꾼 뒤 `r = floor((200·a + s) / (2·s))`, `s = a+b`. 합이 0이면 `null`. 값이 크면 정수 안전 범위를 넘으므로 BigInt를 쓰거나 칸 글자 수를 제한한다. 단위 테스트 표(계약에 적는다): (100,20)→83, (1,1)→50, (1,2)→33, (2,1)→67, (1,7)→13(12.5), (7,1)→88(87.5), (0,5)→0, (5,0)→100, (0,0)→`null`. 부동소수 `Math.round(a/s*100)`은 쓰지 않는다.
- **[0·100 극단값] 수용** — 범위 0~100을 닫힌 구간으로 쓰므로 적금만(100)·ETF만(0)이 그대로 서고, 100이면 ETF 0%라 `scenarios`에 AVG 하나만 오는 기존 목(`get-plan.200-etf0.json`)과 이어진다. 다만 반올림 때문에 **양쪽 모두 입력했는데 0 또는 100이 되는 경우**(예: 적금 1원·ETF 1,000만원 → 0)가 있다. 결과 화면 조건 바가 `display["conditions.savingsRatioPct"]`로 실제 저장값을 보여주므로 막지 않고 둔다(고정 규칙 `1~99로 조임`은 서버 범위와 달라 프론트 하드코딩이 된다). 이 사실을 계약에 한 줄 적는다.
- **[납입액 두 칸의 검증] 수정** — 두 칸은 `rules.yml`에 없는 필드라 서버 422가 없다. 프론트는 형식(C12a-5-6 (d) 정규식)과 음수 불가만 본다. 토글을 켠 채 **두 칸이 모두 비어 있으면 0으로 보고 `null`**(= 비중 유지), 한 칸만 비면 0으로 본다. 이 규칙을 #127에 적지 않으면 `REQUIRED`를 걸어 사용자가 5번에서 막힌다(아래 3번에서 필요).
- **[`savingsRatioPct`를 '요청에 없는 것'에서 뺌, rules.yml `SAVINGS_RATIO_PCT` 추가] 수용** — 소비자는 422 `min`·`max`·`unit`만 읽는다. 단 프론트는 항상 0~100을 만들어 보내므로 이 422는 화면에서 거의 안 난다. 소비자용 목 파일은 불필요(아래 5번).
- **[차액 문구는 "화면 몫"] 반대** — 초안 23행과 #127 수용 기준 5번("차액 30만원도 같은 비중으로 배분했다는 문구")은 화면이 **월 저축 가능 금액 − 납입액 합계**를 계산해야만 만들 수 있다. ① 빼기는 금액 계산이라 NFR-INT-01 위반이다(D-084 예외는 추천 채움에 한정). ② 납입액은 저장하지 않으므로(D-043) 새로고침·재로그인·입력 수정 뒤에는 화면이 합계를 모른다. 수정안: 가정 보기 문구는 **금액 없는 고정 문장** `assumptions.ratioAppliedToAll`("월 저축 가능 금액 전체를 현재 비중({ratio})대로 나눠 계산했어요") + `display["conditions.savingsRatioPct"]`로 한다. 표시 조건은 "납입액을 입력했는지"가 아니라 **계획 `plan.savingsRatioPct`가 null이 아님**(저장된 것만 알 수 있다). #127 5번 수용 기준에서 "30만원"을 뺀다.

### 2. 쟁점 (a): 입력 화면 비중 vs 대화 변경, `STALE_COMPARISON` (요점 2)

- **[초안 주장 "#33에서 이미 구현, 추가 작업 없음"] 수용** — 계약·Issue 기준으로 맞다. 근거: 서버 검사 9(`current_version_id ≠ 기준 버전` → 409, `frontend-api-chat.md:295`, #33 본문), 프론트 처리는 #53 수용 기준 31행("`STALE_COMPARISON`은 그 버튼 비활성 + 토스트 '가장 최근 비교 결과만 적용할 수 있어요'", 계획 화면은 다시 부르지 않음)과 chat 계약 311행. 문구표 키도 **이미 있다**: `copy/copy.ko.yml:91` `toast.applyStaleComparison`. 코드 쪽은 #53이 아직 열려 있고 프론트 코드에 이 키를 쓰는 곳이 없으므로 "구현됨"이 아니라 "계약·AC에 있음"이다. 단 `#33` 머지 여부는 확인하지 못했다(Issue 본문만 봄).
- **[B팀 화면 안내] 수용(보강 1건)** — 같은 탭에서는 사실상 이 409가 나지 않는다. 입력 수정 저장이 성공하면 `revision`이 바뀌어 D-069(chat 337행, #53 7행)가 그때 가진 모든 적용 버튼을 이미 끈다. 새로고침 뒤에는 F-4 `applicable=false`가 서버에서 미리 버튼을 끈다. 409는 **다른 탭에서 입력 저장** 같은 경우에만 남는다. 또한 비중만이 아니라 **입력 저장은 값이 같아도 항상 새 버전**이므로(P-3, 복사 INSERT) 비중 변경이 특별한 경우가 아니다. 이 사실을 초안 쟁점 칸에 적으면 B팀이 "비중 충돌 전용 처리"를 만들 이유가 없어진다.
- **[문구] 수정(키 추가 없이 문장 교체)** — `toast.applyStaleComparison`의 문장 "가장 최근 비교 결과만 적용할 수 있어요"는 원인이 "최신 비교 아님"일 때만 맞다. 원인이 "계획이 입력 화면에서 바뀜"이면 안내가 어긋난다(둘은 같은 코드라 프론트가 가를 수 없다, chat 303행). 한 문장으로 둘 다 덮는다: "계획이 바뀌었거나 더 최근 비교가 있어요. 최신 비교를 다시 받아 적용해 주세요". #53 AC 19행("최신 비교로 다시 하라는 안내")과도 맞는다. 새 키는 필요 없다.
- **[D-085 "나중 변경이 이긴다"와의 일치] 수용** — 입력 저장 → 대화 비교가 stale → 다시 비교 → 적용(마지막 값이 이김)으로 서버가 보장한다. D-041(누적 금지)과 D-033(검증은 Spring)도 그대로다.

### 3. 쟁점 (b): 입력 수정으로 돌아왔을 때 토글 복원 (요점 3)

전제: `plan.savingsRatioPct`는 응답에 있고 납입액 두 칸은 저장되지 않는다. 현재 코드에는 토글이 없고 읽기 전용 줄(`PlanInputPage.tsx:175·327`, `input.currentRatioLabel`)만 있다. "저장을 다시 눌렀을 때"는 토글 켬·납입액 칸 비어 있음/채움 두 경우로 본다.

| 안 | 복원 모양 | 저장을 눌렀을 때 비중 | 문제 |
|---|---|---|---|
| (A) 비중이 `null` 아니면 토글 ON, 납입액 비움, 비중 읽기 전용 | #127 수용 기준 9번과 일치 | 칸을 비운 채 저장 → 합 0 → `null` → **현재 비중 유지**. 칸을 채워 저장 → 새 비중으로 **덮음**. 토글을 끄고 저장 → `null` → **현재 비중 유지**(아래 4번 문제) | 비어 있는 칸이 "비중 유지"를 뜻한다는 설명 필요(`input.ratioKept` 한 줄). 칸이 `REQUIRED`가 되면 안 됨 |
| (B) 항상 토글 OFF 시작, 비중 줄만 안내 | #127 9번과 **불일치**(수용 기준을 바꿔야 함) | 저장 → `null` → 현재 비중 유지(안내 줄이 보이므로 무해) | 비중이 83인데 토글이 "끔(= 5:5)"으로 보여 거짓말이다. 대화로 70이 된 계획에서 입력 수정을 열면 "5:5로 돌아간 줄" 오해 |
| (C) 비중에서 납입액 역산 | 칸에 금액이 보임 | 저장 → 역산한 금액으로 비중 재계산 | **반대**. 월 저축 가능 금액 × 비중은 금액 계산이라 NFR-INT-01 위반(D-084 예외도 해당 없음). 역산 금액은 사용자가 낸 적 없는 가짜 값이고, 원 단위 반올림 때문에 저장 후 비중이 1 흔들릴 수 있다. 납입액을 저장하지 않는다는 D-043과도 어긋난다 |

**의견: (A) 수용(수정 두 가지).**
1. 토글 ON 복원 상태에서 두 칸이 모두 비어 있으면 **오류가 아니라 "현재 비중 유지"**다. 칸 아래 도움말 `input.ratioKept`("납입액을 비워 두면 현재 비중을 그대로 써요")를 둔다.
2. 토글을 직접 **끄는** 동작은 `null`이 아니라 4번처럼 처리한다.
- 계약 C12a-7 입력 수정 행(490행)에 위 두 가지와 "납입액 칸은 복원하지 않는다(D-043)"를 한 줄로 적는다. 토글 ON 복원의 조건은 `plan.savingsRatioPct !== null`뿐이며 값이 `50`이어도 켠 상태다(사용자가 정했거나 대화로 50이 된 것과 첫 저장 `null`을 응답으로 구분할 수 있다).

### 4. 쟁점 2: 기본 비중 구멍 (요점 4)

- **[현 초안 "직전 비중 유지"] 반대(사용자 입장에서 납득되지 않음)** — SRS는 "끄면 5:5 기본 비중이다"(`srs.md` FR-INP-08, D-085)이고 #127 수용 기준 2번도 "토글 끔 → 서버 기존 규칙(현재 버전 값 복사)"이라 서로 어긋난다. 사용자는 "껐으니 5:5"로 기대하는데 83이 남는다. 결과 화면 조건 바가 "적금 83 : ETF 17"을 보여 주므로 잘못된 숫자는 아니지만 "토글이 꺼져 있는데 비중이 있다" 상태가 UI에서 설명되지 않는다.
- **[그렇다고 화면이 항상 50을 보내는 안] 반대** — 토글 OFF를 무조건 50으로 보내면 대화로 70이 된 사용자가 월 저축액만 고쳐 저장해도 비중이 5:5로 되돌아간다. 이는 D-085의 "나중 변경이 이긴다"가 아니라 의도하지 않은 덮어쓰기다. `null`=복사(R-9)가 존재하는 이유가 이것이다.
- **수정안(작게)**: 프론트는 세 상태만 안다. ① 토글을 한 번도 안 건드림(복원 ON이면 비운 칸 = 유지, 복원 OFF면 첫 저장) → `null`. ② 토글 ON + 납입액 입력 → 계산한 비중. ③ **복원 때 ON이었던 토글을 사용자가 직접 끔** → `50`(5:5)을 보낸다. 끌 때 화면에 `input.ratioResetNote`("끄면 적금 5 : ETF 5로 돌아가요", 기존 `ratio` 틀 재사용)를 보여 줘 동작이 예고된다. 이렇게 하면 "끄면 5:5"가 참이고, 토글을 안 건드리는 일반 수정은 대화 변경 비중을 지키며, `null` 의미(R-9)는 그대로다.
- 이때 `50`이라는 값이 프론트에 하드코딩되는데, 이는 서버의 `NULL = 5:5`와 중복된 지식이다. 최소 비용으로 처리: 계약 C12a-5-1에 "`50`은 서버가 `NULL`로 보는 5:5와 같은 결과이고 프론트 상수 `DEFAULT_SAVINGS_RATIO_PCT = 50` 하나만 쓴다"를 적고 테스트로 고정한다(`plan_version` 컬럼은 `NULL` 대신 `50`이 저장될 뿐 계산 결과는 같다). 제공자 쪽 질문은 "`50`과 `NULL`이 모든 소비처(planContext·대안·`display`)에서 같게 취급되는가"다. 같다면 Q 필요 없이 이 안으로 닫을 수 있다. 다르면 R-9에 "NULL이 5:5"를 `50`으로 정규화하는 규칙을 더한다.
- 초안 47행의 "Q로 올릴 후보"는 **소비자 쪽에서는 위 수정안이면 Q 불필요**다. 단, 제공자가 반대하면 Q로 올린다.

### 5. 목 파일·문구표 (요점 5)

- **목 파일: 1개 추가, 29 → 30개 수용** — 요청 오류 쪽은 필요 없다. 필요한 것은 복원 시험용 `plan/get-plan.200-ratio83.json`(P-4, `plan.savingsRatioPct: 83`, `display["conditions.savingsRatioPct"]: "적금 83 : ETF 17"`, `baselineResultScenario` 등은 기본 목 복사). 지금 목은 `null`·`50`·`100`(etf0)만 있어 "ON으로 복원 + 읽기 전용 줄 + 칸 비어 있음" 시험이 `50`만으로는 `null`과 구분되지 않는다. 이 파일이 있으면 #127 수용 기준 9번(복원)과 위 4번 ③(끄면 `50`)이 목만으로 확인된다. README 개수와 `mocks.test.mjs`의 목록도 함께 바꾼다.
- **요청 본문 검증은 파일이 아니라 단위 테스트** — 목은 응답 고정 JSON이라 요청을 검증하지 못한다. 3번의 산출 표와 "토글 OFF `null`/복원 ON 비움 `null`/ON 채움 값/복원 ON을 끔 `50`" 네 경우를 `features/input` 테스트에 둔다. 요청 본문 기대값은 테스트에서 확인한다.
- **문구표 추가가 필요한 키(#18·`copy.ko.yml`)**: 현재 `input.currentRatioLabel`만 있고 아래가 없다(`copy.ko.yml` 106~125행 확인).

## 소비자 쪽에서 꼭 필요한 것
1. 비중 산출의 **정수 연산·HALF_UP·단위 테스트 표**를 계약에 적을 것(1번). 안 적으면 프론트가 부동소수로 짜고 값이 갈린다.
2. D-085(또는 NFR-INT-01 비고)에 **비중 산출은 입력 보조 계산이라는 예외 한 줄**(1번). 없으면 이후 검토에서 같은 논쟁이 반복된다.
3. 가정 보기 문구에서 **차액 금액을 빼고** 고정 문장으로(1번). 안 그러면 화면이 빼기를 하거나 서버 필드가 새로 필요하다.
4. 토글 OFF 의미 정리(4번): **복원 때 ON이던 토글을 직접 끄면 `50`**. 아니면 "끄면 5:5" 문장이 거짓이다.
5. 복원 때 **두 칸이 비면 `null`(비중 유지)**이라는 규칙(3번). 아니면 토글을 켠 사용자가 납입액을 다시 내야만 저장할 수 있다.
6. 요청 본문에 `savingsRatioPct` **키가 항상 있다**는 사실을 #48·목·계약 예시에 반영(1번).
