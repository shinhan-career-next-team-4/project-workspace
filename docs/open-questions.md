# 미결 질문

## 질문 형식
```
### Q-번호: [한 줄 질문]
- 관련: FR-xxx
- 심각도: 개발 차단 / 개발 중 혼란 / 사소함
- 왜 문제인가:
- 선택지: A) ... / B) ...
- 상태: 미결
```

## 1차 검증 (2026-11-16, spec-verifier + finance-domain-reviewer)

> 이미 SRS 비고에 미결로 적힌 TBD(예: TBD-09 범위 수치, TBD-33 시간 초과, TBD-40 기준 시나리오 기본값)는 다시 올리지 않았습니다. 아래는 정의서에 아직 드러나지 않은 문제입니다.

### Q-002: 목표 기간을 정하지 않은 사용자에게 결과 화면은 무엇을 보여주나?
- 관련: FR-INP-04, FR-RES-02, FR-RES-04, FR-RES-08, FR-ALT-02, D-005, TBD-14/39
- 심각도: 개발 차단
- 왜 문제인가: D-005로 목표일은 선택 입력인데, 결과 요약(FR-RES-02)은 "목표일의" 예상 자산, 필요 월 저축액(FR-RES-08)은 "목표 기간 안에", 대안 카드(FR-ALT-02)는 "기한을 늘리면"을 전제로 한다. 기한이 없으면 이 화면들의 내용이 정의되지 않는다.
- 선택지: A) 기한이 없으면 "목표 도달 시점(CP-01)"을 대신 보여주고, 그래프 끝은 도달 시점까지, '기한을 늘리면' 카드는 숨김 / B) 기한이 없으면 내부 기본 기간(예: N년)을 가정하고 가정 보기에 표시 / C) 기한 입력을 필수로 바꿈(D-005 변경)
- 상태: 결정됨 → D-008

### Q-003: 월 저축 가능 금액을 "잘 모르겠어요"로 답하면 계산에 어떤 값을 쓰나?
- 관련: FR-INP-06, FR-RES-02, FR-RES-03, FR-RES-04, FR-RES-08, FR-ALT-01, TBD-12
- 심각도: 개발 차단
- 왜 문제인가: 월 저축액이 없으면 예상 자산, 3구간, 그래프, 달성/미달 판정을 계산할 수 없다. FR-RES-08(필요 월 저축액)만 정의돼 있고 나머지 결과 영역의 동작이 없다. Q-002와 겹치면(기한도, 월 저축액도 모름) 계산 입력이 목표 금액과 보유 자산뿐이다.
- 선택지: A) 필요 월 저축액을 계산해 그 값으로 나머지 결과를 채우고 "필요 월 저축액 기준" 라벨 표시 / B) 결과 화면은 필요 월 저축액만 보여주고 나머지 영역은 숨김 / C) 기한과 월 저축액을 둘 다 모르면 진행을 막고 둘 중 하나를 입력받음
- 상태: 결정됨 → D-009

### Q-004: 재로그인 시 "시작월 고정(D-004)"과 "최신 데이터로 재계산(FR-PLAN-05)"을 함께 적용하면, 이미 지난 달들은 어떻게 처리하나?
- 관련: FR-PLAN-05, D-003, D-004, NFR-INT-02, TBD-23, TBD-38
- 심각도: 개발 차단 (계산 API 계약에 직접 영향)
- 왜 문제인가: 3월에 저장하고 5월에 다시 로그인하면, 시작월은 3월로 고정되지만 3~4월에 실제로 저축했는지는 모른다. 또 D-003은 "요청이 들어온 날" 기준인데 시작월은 "월" 단위다. 말일 요청이 그 달인지 다음 달인지도 정해져 있지 않다.
- 선택지: A) 지난 달도 계획대로 저축했다고 가정하고 계산(가정 보기에 표시) / B) 지난 달은 무시하고 현재 월부터 남은 기간으로 다시 계산(시작월은 표시용) / C) 재로그인 시 "그동안 계획대로 저축했나요?"를 묻기
- 추가로 정할 것: 요청일이 속한 달을 시작월로 볼지, 다음 달을 시작월로 볼지
- 상태: 결정됨 → D-010

### Q-005: AI 대화로 바꾼 조건은 내 계획에 어떻게 적용되나?
- 관련: FR-AI-06, FR-AI-07, FR-PLAN-01~03, CP-02, CP-07
- 심각도: 개발 차단 (프론트, AI 서버, 백엔드 사이 흐름)
- 왜 문제인가: FR-AI-07은 대화로 바꾼 조건의 재계산 결과를 "대화창에" 보여준다고만 한다. 이 결과가 비교용 임시 결과인지, 내 계획을 바꾸는지, 바꾼다면 FR-PLAN-01의 확인창을 거치는지가 없다. 대화에서 받은 값이 CP-02 허용 범위를 벗어날 때의 동작(되묻기 / 거부 / 범위 끝값으로 보정)도 없다.
- 선택지: A) 대화 결과는 비교용. 대화창에 '내 계획으로 적용' 버튼을 두고 FR-PLAN-01 확인창으로 연결 / B) 대화 결과는 대화창 안에서만 보여주고 적용 기능 없음 / C) 대화로 바꾸면 바로 내 계획에 반영(확인창 없음)
- 상태: 결정됨 → D-011

### Q-006: 적금 기본 금리는 어떤 상품, 어떤 기간의 은행연합회 평균금리를 쓰나?
- 관련: FR-DATA-01, FR-INP-07, CP-03, TBD-07
- 심각도: 개발 차단 (데이터 수집 형식 결정) — TBD-07에 이미 정해져 있다면 원문 확인 필요
- 왜 문제인가: 은행연합회 공시 금리는 상품(정기적금, 자유적립식)과 가입 기간(6·12·24·36개월)마다 다르다. 목표 기간은 사용자마다 다르고 몇 년이 될 수도 있어서, 어떤 값을 "기본 금리"로 쓸지 정해야 한다. 적금 만기보다 목표 기간이 길 때 재가입을 가정하는지도 정해야 한다.
- 선택지: A) 12개월 정기적금 평균 하나로 고정, 목표 기간 동안 같은 금리로 매년 재가입 가정 / B) 목표 기간에 가장 가까운 가입 기간의 금리 사용
- 상태: 결정됨 → D-012

### Q-007: S&P500 과거 데이터는 달러 지수 그대로인가, 원화로 환산한 값인가?
- 관련: FR-DATA-02, FR-RES-03, CP-03, D-007, TBD-01, TBD-05
- 심각도: 개발 중 혼란 — TBD-05에 정해져 있다면 원문 확인 필요
- 왜 문제인가: 근거 자료로 검토 중인 KODEX, TIGER S&P500(D-007)은 원화로 사고파는 국내 상장 ETF라 환율 변동이 수익에 들어간다. 달러 지수로 3구간을 계산하면 실제 사용자가 경험하는 결과와 다를 수 있다.
- 선택지: A) 원화 환산 지수 사용 / B) 달러 지수를 사용하고 가정 보기에 "환율 변동 미반영" 표시
- 상태: 결정됨 → D-027 (임시, Claude 판단 (진혁 위임))

### Q-008: [도메인] AI 설명과 출처에 특정 ETF 상품명(KODEX, TIGER 등)을 노출해도 되나?
- 관련: FR-AI-03, FR-AI-10, CP-06, NFR-USA-02, D-007, PR-05
- 심각도: 개발 중 혼란
- 왜 문제인가: CP-06은 특정 금융상품을 권유하거나 골라주지 않는다고 정했는데, FR-AI-03은 운용사 공시 자료를 출처로 보여준다. 출처에 상품명이 나오면 사용자가 "이 상품을 사라"로 받아들일 수 있다. 화면의 "ETF"가 특정 상품이 아니라 "S&P500 추종 ETF 일반"이라는 점도 정의서에 명시돼 있지 않다.
- 선택지: A) 출처 링크에는 상품명을 그대로 보여주되, 본문 설명에서는 상품명을 쓰지 않고 "S&P500 추종 ETF"로만 표현 / B) 출처도 운용사·문서명까지만 표시하고 상품명 노출 금지
- 상태: 결정됨 → D-028 (임시, Claude 판단 (진혁 위임))

### Q-009: [도메인] 3구간 결과 영역에 과거 수익률 고지를 따로 보여줘야 하나?
- 관련: FR-RES-03, FR-RES-07, CP-05

- 왜 문제인가: 면책 문구는 결과 화면 맨 아래에만 있다(FR-RES-07). '좋았던 때' 금액이 크게 보이면 기대 수익으로 오해하기 쉬운데, 근처에 "과거 데이터 기준이며 미래 수익을 보장하지 않음" 안내가 없다.
- 선택지: A) 3구간 영역 바로 아래에 한 줄 고지를 추가(문구표 CP-05에 등록) / B) 맨 아래 면책 문구로 충분
- 상태: 결정됨 → D-029 (임시, Claude 판단 (진혁 위임))

### Q-010: [도메인] 사용자 입력값 중 어떤 값을 LLM에 넘기고, 대화 기록은 어디에 얼마나 저장하나?
- 관련: NFR-INT-03, FR-AI-06, NFR-SEC-01~02
- 심각도: 사소함 (데모 계정만 쓰므로 MVP 위험은 낮음, 정책 한 줄은 필요)
- 왜 문제인가: 보안 요구사항은 비밀번호와 세션만 다룬다. 목표 금액, 보유 자산 같은 금융 입력값이 외부 LLM API로 전달되는 범위와 대화 기록 보관 정책이 없다. 금융권 포트폴리오에서 질문받기 쉬운 지점이다.
- 선택지: A) LLM에는 계산 결과와 조건만 넘기고 계정 식별 정보는 넘기지 않음, 대화 기록은 세션 동안만 보관 / B) 대화 기록을 DB에 저장(되돌아보기용), 보관 기간 명시
- 상태: 결정됨 → D-030 (임시, Claude 판단 (진혁 위임))

### Q-011: '약 N만원' 반올림 때문에 "약 0만원 미달"처럼 보이는 경우는 어떻게 표시하나?
- 관련: CP-04, CP-01
- 심각도: 개발 중 혼란
- 왜 문제인가: CP-01은 목표 대비 0원을 달성으로 본다. 실제로 3천 원이 부족하면 판정은 미달인데, '약 N만원' 표시로는 "약 0만원 · 미달"이 된다. 반올림인지 버림인지도 정해져 있지 않다.
- 선택지: A) 1만원 미만 차이는 "1만원 미만 부족 / 초과"로 표시 / B) 판정도 만원 단위로 반올림한 값으로 함
- 추가로 정할 것: 만원 단위 반올림 / 버림 / 올림 중 무엇을 쓸지
- 상태: Notion TBD-16으로 통합 (반올림은 천 단위로 정해져 있고, 판정에 반올림 전/후 중 무엇을 쓸지가 TBD-16에서 미결)

### Q-012: AI 설명을 기다리는 동안에도 30분 무조작 로그아웃 시간이 흐르나?
- 관련: FR-AUTH-02, NFR-SEC-02, FR-AI-01, FR-AI-04
- 심각도: 사소함
- 왜 문제인가: "조작"의 정의(클릭, 입력, 스크롤, 서버 요청)가 없다. 프론트 타이머와 서버 세션 만료가 따로 돌면, AI 응답이 도착한 직후 요청이 만료 세션으로 거절될 수 있다.
- 선택지: A) 서버로 가는 요청만 조작으로 보고, 서버 세션 만료 시간을 기준으로 함 / B) 화면 조작(클릭, 입력)도 조작으로 보고 프론트에서 세션 연장 요청을 보냄
- 상태: 결정됨 → D-031 (임시, Claude 판단 (진혁 위임))

### Q-013: ETF 비중이 0%(적금만)일 때 기준 시나리오 선택은 어떻게 되나?
- 관련: FR-RES-03, FR-RES-09, FR-ALT-01, FR-CMP-01

- 선택지: A) ETF 0%면 기준 시나리오 선택을 숨김 / B) 선택은 보이되 비활성화하고 이유를 표시

### Q-014: 재로그인 후 최신 데이터로 다시 계산해서 결과가 바뀌면 사용자에게 알려야 하나?
- 관련: FR-PLAN-05, NFR-INT-02, FR-RES-06
- 심각도: 사소함
- 왜 문제인가: 금리나 지수 데이터가 갱신되면 같은 계획인데 숫자가 달라진다. 데이터 버전은 기록하지만(NFR-INT-02) 사용자에게 보여주는 요구사항이 없어서, 숫자가 왜 바뀌었는지 알 수 없다.
- 선택지: A) 가정 보기(FR-RES-06)에 데이터 기준일을 표시 / B) 이전 계산과 결과가 달라졌을 때 결과 화면 상단에 한 줄 안내

### Q-016: 목표 기간이 없을 때(D-008) 결과 화면의 나머지 영역(3구간, 그래프, 판정, 대안)은 어떻게 바뀌나?

- 왜 문제인가: D-008은 결과 요약에 "목표 금액까지 걸리는 시간"을 보여준다는 것만 정했다. Q-002 선택지 A에 있던 세부 내용(그래프 범위, '기한을 늘리면' 카드 숨김)은 채택되지 않았고, FR-RES-04 비고에도 그래프 범위가 미정으로 남아 있다. 기한이 없으면 "목표일의 예상 자산"이 없고 달성/미달 판정(FR-RES-09)과 대안 표시 조건(FR-ALT-01, "목표에 못 미칠 때")도 성립하지 않는다.
- 선택지:
  - A) **도달 시점 중심**: 결과 요약은 기준 시나리오(TBD-40 기본 평균)로 계산한 도달 시점. 3구간은 시나리오별 도달 시점("좋았던 때 n년 n개월 / 평균 / 나빴던 때"). 그래프는 계산 시작월부터 나빴던 때 도달 월까지. 달성/미달 판정과 대안 영역은 숨김. → 계산 API는 "기간 → 금액" 외에 "금액 → 기간" 역계산이 필요. 화면은 기한 유무로 두 갈래.
  - B) **A + 대안 영역 유지**: A와 같되, 대안 영역은 숨기지 않고 '월 저축액을 늘리면 / 비중을 바꾸면 n개월 빨라져요' 2종만 표시('기한을 늘리면' 카드 숨김). → FR-ALT-01 표시 조건과 FR-ALT-02 '세 대안 나란히'를 기한 없음 경우에 맞게 고쳐야 함. 작업량 증가.
  - C) **기본 기간을 가정하지 않고 도달 시점만 표시**: 결과 요약의 도달 시점만 보여주고 3구간·그래프·대안은 모두 숨김. → 가장 단순하지만 기한 없는 사용자는 결과 화면 대부분이 비어 보임.
- 추가로 정할 것:

### Q-018: 재로그인 후 비교·대안·대화로 새로 계산할 때는 어떤 기준 데이터를 쓰나? (D-010 이후)

  - C) **새 계산이 일어나면 내 계획도 최신 데이터로 갱신**: 재로그인 직후는 스냅샷, 비교·적용 등 새 계산이 일어나면 그때 내 계획 전체를 최신 데이터로 다시 계산. → D-010의 범위를 "로그인 직후 표시"로 좁히는 해석이라 D-010 확인 필요.

- 상태: 결정됨 → D-017 (답변은 '대화로 새로 계산할 때' 기준. 비교·대안 계산도 같은지는 4차 검증에서 확인)

### Q-019: 어떤 동작이 시작월을 새로 정하나? 그리고 TBD-38의 '결과반영' 버튼은 남기나?

- 왜 문제인가: D-024와 SRS(FR-RES-02·08)는 모름 사용자의 결과 화면에 "필요 월 저축액과 3구간 결과**만**" 보여준다고 썼다. 글자 그대로면 면책 문구(FR-RES-07, 항상 표시), 조건 바(FR-RES-05), 가정 보기(FR-RES-06), AI 설명(FR-AI-01)도 빠진다. 또 비교 영역(FR-CMP-02)과 대화 비교(FR-AI-07)는 결과마다 목표 대비와 달성/미달(TBD-20)을 보여주는데, 모름 계획의 "현재 조건" 칸은 판정을 숨겨야 하므로 비교표를 같은 형식으로 만들 수 없다. 사용자가 비교나 대화로 "월 50만원이면?"이라고 하거나 그 결과를 적용하면 내 계획이 일반 계획(월 저축액 있음)으로 바뀌는지, 되돌리기(FR-PLAN-04)로 모름 상태로 돌아가는지도 정해져 있지 않다. 재로그인 후 D-018·D-021의 '다시 계산'(대화나 결과 그래프로 조건 변경)도 그래프가 없는 모름 사용자에게는 어떤 경로인지 없다.

  - B) **비교·대화 허용, 월 저축액을 넣으면 일반 계산**: 바꾼 조건에 월 저축액이 있으면 그 칸은 일반 결과(판정 포함)로, 없으면 X를 다시 계산해 보여준다. "현재 조건" 칸은 X와 3구간만(판정 칸 비움). 월 저축액이 들어간 결과를 적용하면 내 계획이 일반 계획으로 바뀌고 일반 결과 화면으로 넘어간다. 되돌리기는 모름 상태로 돌아간다. → 내 계획에 '모름/알아요' 상태와 전환 규칙이 필요하고, 비교표가 칸마다 형식이 달라짐. 작업량 가장 큼.
  - C) **비교·대화는 월 저축액 외 조건만**: 모름 상태를 유지한 채 기한·비중·적금 금리만 바꿔 "그러면 필요 월 저축액은 약 N만원"을 보여준다. 월 저축액을 말하면 A처럼 입력 수정으로 안내. → 모름 사용자에게 가장 쓸모 있는 비교(기한을 늘리면 X가 얼마로 주는지)를 주지만, 비교 API에 역계산(X 다시 계산) 경로가 추가됨.
- 추가로 정할 것:
  1. 조건 바(FR-RES-05)의 월 저축액 칸에 무엇을 보여주는지: "모름" / "필요 월 저축액 약 N만원".
  2. 내 계획에 저장하는 값: '모름' 표시만 저장하고 X는 매번 다시 계산 / X도 함께 저장. 재로그인 시 D-010(다시 계산하지 않음)을 지키려면 X를 저장하는 쪽이 자연스럽다.

### Q-036: 판정을 숨긴 채(D-024) 3구간으로 "나빴던 때 모자랄 수 있다"는 위험을 어떻게 보여주나?

  - A) **500처럼 처리**: `common.networkError` 토스트, 입력값 유지, `loadPlan()`을 부르지 않는다 → 구현이 가장 적지만, 서버가 저장했다면 다시 눌렀을 때 409 안내가 잘못 나온다(두 번째 누름에서 저장되므로 데이터는 맞음).

  - C) **B + 저장됐으면 결과 화면으로**: `loadPlan()` 결과의 `plan` 값이 입력값과 같으면 결과 화면으로 넘어간다 → 사용자에게 가장 자연스럽지만 입력값 비교 규칙(만원 변환 포함)이 추가된다.

### Q-066: D-076의 "허용 출처" 설정은 무엇을 검사하고, 로컬 기본값은 무엇인가? JWT 서명 키가 설정에 없으면 서버는 어떻게 하나?

### Q-067: 금액 칸에 자릿수가 아주 큰 값을 넣으면 누가, 무엇으로 막나?
- 관련: CP-02, FR-INP-09, FR-INP-03·05·06, frontend-api-plan.md C12a-5-1(`JsonNode`로 받음)·C12a-5-4("범위 수치는 하드코딩하지 않음")·C12a-5-6 (d), moeun #17, #19, #48
- 심각도: 개발 중 혼란 (#48 변환 util, #17 검증기. 잘못 구현하면 범위 밖 값이 범위 안 값으로 저장됨)
- 왜 문제인가: 만원 칸 형식 `^\d+(\.\d{1,4})?$`는 자릿수 제한이 없고, 범위 검사는 서버가 422로만 한다(CP-02). 그런데 (1) 프론트가 원 정수 문자열을 JS `Number`로 바꾸면 2^53(약 9천조 원)을 넘는 값은 다른 숫자로 바뀌어 전송되고, (2) 서버가 `JsonNode`의 큰 정수를 `asLong()`/`longValue()`로 읽으면 64비트 밖 값은 아래 자리만 남아 **범위 안 값(예: 384원)으로 둔갑**해 `heldAssets`(0~100억) 검사를 통과할 수 있다. SRS·계약 어디에도 "long 범위 밖·지나치게 큰 값"의 처리가 없다.
- 선택지:
  - A) **서버에서 막음**(추천): 정수 필드가 `long` 범위 밖이거나 `BigInteger`·`BigDecimal`이면 `OUT_OF_RANGE`(같은 `min`·`max`)로 돌려주고, 프론트는 문자열 연산 결과를 JSON 숫자로 그대로 싣는다(`Number` 변환 없이) → #17에 테스트 1~2개, CP-02 "서버 한 곳 검증"과 맞음.
  - B) **프론트가 자릿수로 먼저 막음**: 만원 칸 정수부를 예: 9자리까지로 제한하고 넘으면 `input.invalidAmountFormat` → 서버 보완이 없으면 API 직접 호출은 여전히 둔갑 가능, 계약의 "범위 수치 하드코딩 안 함"과 어긋남.
  - C) A + B 둘 다.
- 상태: 결정됨 → D-080

### Q-068: 직접 입력 목표명 검증의 세부(빈 값의 오류 종류, 글자 수 기준, 저장 값, CUSTOM이 아닐 때)는?
- 관련: FR-INP-02, CP-02, D-074, D-075, TBD-09, frontend-api-plan.md C12a-5-1·5-4·5-5, moeun #17, #19, #48

- 선택지:
  - A) **빈 값·공백뿐 → `REQUIRED`, 초과 → `OUT_OF_RANGE`, trim한 값 저장, UTF-16 기준(계약 그대로), `CUSTOM`이 아니면 검증 없이 `null` 저장. CP-02 수용 기준은 FR-INP-02를 구현하기 전까지 API 테스트로 확인**(추천) → 계약 문장 2줄 보충.
  - B) 빈 값도 `OUT_OF_RANGE`(min 1)로 하나로 묶음 → 안내 문구가 "1~100자"로 통일되지만 다른 필수 필드(`REQUIRED`)와 규칙이 달라짐.
- 상태: 결정됨 → D-081

### Q-070: JSON 숫자 `300000.5`와 문자열 금액은 `NOT_INTEGER`/`400`인가, `OUT_OF_RANGE`인가? (CP-02·FR-INP-09 수용 기준 vs 계약 본문)
- 관련: CP-02, FR-INP-09, D-080, Q-067, frontend-api-plan.md C12a-5-2 순서 1·2, C12a-5-4 422 예시 2, 머리말 보충 D-080, moeun #17, #48
- 심각도: 개발 차단 (#17 검증기 테스트 기대값이 세 문서에서 갈림)
- 왜 문제인가: Q-067 선택지 A(D-080의 근거)는 "`long` 범위 밖이거나 `BigInteger`·`BigDecimal`이면 `OUT_OF_RANGE`", 즉 **자릿수가 큰 정수**만 다뤘다. 그런데 D-080 문장·계약 보충은 "정수가 아닌 숫자 타입 → `OUT_OF_RANGE`"로 넓게 적혔고, SRS CP-02 수용 기준(D-080 두 번째 줄)은 "`300000.5`나 **문자열**이 담긴 요청 → `OUT_OF_RANGE`"로 정했다. 계약 본문은 같은 입력을 `300000.5` → 422 `NOT_INTEGER`(C12a-5-4 예시 2, C12a-5-2 순서 2), 문자열 → 400 `MALFORMED_REQUEST`(C12a-5-2 순서 1)로 정했고, CP-02 설명 문장도 "정수가 아닌 값은 입력 검증 오류"(= `NOT_INTEGER`)다. 보충은 "본문보다 우선"이라 #17이 수용 기준을 테스트로 옮기면 어느 쪽을 써도 다른 문서와 어긋나고, 프론트(#48)의 `validation.NOT_INTEGER` 안내·400 토스트 분기도 정해지지 않는다.
- 선택지:
  - A) **D-080을 Q-067 원래 범위로 좁힘**(추천): `OUT_OF_RANGE`는 정수값이지만 `long` 범위 밖(`BigInteger`, 정수값인 큰 `BigDecimal`)일 때만. `300000.5`는 지금 계약대로 422 `NOT_INTEGER`, 문자열은 400 `MALFORMED_REQUEST` → 계약 본문·#17·#48 그대로, SRS CP-02 수용 기준 1줄과 FR-INP-09 문장, D-080·계약 보충 문장만 정정(D-번호로 보충 기록).
