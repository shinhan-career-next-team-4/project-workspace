> 작성: scope-prioritizer, 2026-11-16. **제안이며, 최종 결정은 팀이 합니다.** 결정은 `open-questions.md`의 Q-040으로 받습니다.

## 0. 한눈에 보기
- 현재 우선순위는 **Must 60 / Should 7 / Could 1**입니다. 68건 중 60건이 Must라서 우선순위가 범위를 줄이는 역할을 거의 못 합니다.
- 제안은 **Must 48 / Should 18 / Won't 2**이고, 여기에 더해 **Must 행 안의 분기 4개를 이번 해커톤에서 뺄 것**을 제안합니다.
  - **2026-11-20 갱신(D-084·D-085)**: 2주차 말 점검에서 FR-INP-08을 Won't에서 **Must**로 되살려 **Must 49 / Should 18 / Won't 1**이 되었습니다. 뺀 분기 4개는 그대로 두되, 기간·월 저축액을 모르는 사용자는 분기 대신 **입력 화면의 추천 채움**(D-084)으로 처리합니다. 계약·서버·계산 엔진은 바뀌지 않습니다.
  - 빼는 분기: 오래된 계획 질문, 월 저축액 모름, 기한 없음, 과거 데이터 버전 보관
- 표의 `Must*`는 "행은 Must지만 본문의 특정 분기는 뺀다"는 뜻입니다.
- **결정 충돌 주의**: 이 제안은 D-005(목표일 선택 입력), D-024·D-025(모름 분기), D-026(기한 없음), D-044(FR-RES-08 Must)의 구현 범위와 부딪힙니다. 결정을 뒤집는 대신 "이번 해커톤에서는 구현하지 않음(SRS에는 유지)"으로 처리할 수 있는지 팀이 정해야 합니다(Q-040).

## 2. 3주 일정 위험이 큰 묶음

공통 원인은 **결과 화면의 경우의 수가 늘어난다**는 점입니다. 기한 있음/없음, 월 저축액 입력/모름, ETF 포함/미포함이 서로 곱해지고, 경우마다 계산 API·화면·AI 설명·테스트가 따로 필요합니다.

| 묶음 | 위험도 | 늘어난 작업 | 제안 |
|---|---|---|---|
| 월 저축액 모름 (D-024·D-025·D-042·D-043) | 가장 큼 | 필요 월 저축액 역계산, 만원 올림 후 3구간 재계산, 상한 처리, 그래프·판정·대안 숨김, 전용 라벨·위험 문구, 조건 바·AI 설명 변형, 일반 계획 전환. SRS 약 12행에 영향. TBD-40 미결 | Should 또는 Won't. 입력에서 "잘 모르겠어요" 선택지를 빼면 영향 행이 대부분 사라짐 |
| 기한 없음 (D-026) | 큼 | 금액→기간 역계산, 시나리오 3개 도달 시점, 상한 N년(TBD-39), 판정·대안 숨김, 비교 "현재 조건" 칸 변경. 관측 10년(TBD-01)보다 긴 도달 시점은 외삽이 필요 | Should. 빼면 입력에서 기간을 필수로 받아야 해서 D-005와 충돌 → 팀 결정 필요 |
| 대화 즉시 비교·적용 (D-019·D-022·D-033·D-041) | 큼 (핵심 흐름이라 유지) | FastAPI→Spring 검증 오류 되묻기, LLM 조건·값 추출, 최신 결과만 적용, 토스트, 되돌리기 | Must 유지. 데모 시나리오를 고정하고 LLM 비결정성 대응(검증·재시도)을 일정에 넣기 |
| 데이터 버전 보관 (D-017·D-038) | 중간 | 모든 계산 API에 버전 파라미터, 금리·지수 버전별 보관. 3주 동안은 데이터가 갱신되지 않아 데모에서 차이를 보이려면 일부러 두 번째 버전을 만들어야 함 | 계획에 버전 값 하나만 저장하고 가정 보기에 기준월 표시. 버전별 보관은 Should |
| 오래된 계획 질문 (D-018·D-037) | 중간 | 3개월·목표일 경과 판정, "한 번만" 상태 저장, 고정 문구·버튼, 재계산 연결. 시간이 지나야 나타나서 시연과 테스트가 어려움 | Won't |

## 3. 핵심 흐름이 3주 안에 동작하는가

- **현재 Must 60건 그대로는 어렵습니다.** 백엔드 1명이 계산 엔진, 인증, 데이터, 계획 저장 API, 분기 조합을 모두 맡게 되어 계산 엔진이 병목입니다. 마지막 3~4일을 통합에 쓰면 실제 개발 기간은 11~12일 정도입니다.
- **제안 범위(Must 48건 + 분기 4개 제외)는 가능하다고 봅니다.** 흐름은 "입력 → 기한 있는 계산 → 결과·3구간·그래프 → AI 설명 → 대화로 조건 바꾸기 → 적용·되돌리기"입니다. 단, 조건이 세 가지 있습니다.
  - TBD-01 등 계산 엔진 전제를 1주차 초반에 확정
  - FastAPI↔Spring 연동 계약(검증 오류 형식 포함)을 1주차에 확정하고, 목 서버로 프론트·AI 병렬 개발
  - 데모 시나리오 3~4개를 고정하고 끝까지 리허설
- 이 판단은 정밀한 일정 추정이 아니라 행 수와 분기 구조로 본 것입니다. **2주차 말에 진행률을 보고 Should를 되살릴지** 정하는 방식을 권합니다.

### 빼는 순서 (먼저 뺄 것부터)
1. 오래된 계획 질문 (FR-PLAN-06 일부, FR-PLAN-05의 3개월 규칙, D-018·D-037)
2. 이미 저축 중인 납입액 토글 (FR-INP-08). CF-08 결정도 불필요해짐
3. 월 저축액 모름 분기와 FR-RES-08 (D-024·D-025·D-042·D-043·D-044)
4. 기한 없음 분기 (D-005·D-008·D-026 중 구현 부분)
5. 과거 데이터 버전 보관·재사용 (D-017·D-038). 버전 값 기록은 유지
6. 대안 영역과 비교 영역 (FR-ALT-01~04, FR-CMP-01~03, FR-PLAN-01·02). 2주차 말 여력이 있으면 FR-CMP-02 → FR-ALT 순으로 되살림
7. 기준 시나리오 선택 UI (FR-RES-09), 설명 다시 요청 (FR-AI-05)

## 5. 예상 위험 3가지
1. **계산 엔진 병목과 미결 전제.** Spring 계산 엔진이 백엔드 1명에게 몰리고 TBD-01·04·05가 미결입니다. 완화책: 미확정 1명을 Spring 쪽에 배치하고, 1주차에 계산 명세·손계산 케이스·API 계약·목 서버를 만듭니다.
2. **3서버 통합과 LLM 비결정성.** 프론트→FastAPI→Spring→FastAPI→프론트 경로에서 조건 추출 오류, 되묻기 루프, 숫자 불일치(FR-AI-02·PR-04), 지연이 겹칩니다. 완화책: 숫자 자동 대조, 데모 시나리오 고정, 실패 안내 문구, 전체 리허설 최소 1회.
3. **데이터·RAG 확보와 문구 위험.** 자료 이용 가능 여부(TBD-08)가 불확실하고 RAG 문서가 2건뿐입니다. LLM이 추천 금지(CP-06)나 상품명 규칙(D-028)을 어기면 금융 데모로서 치명적입니다. 완화책: 1주차 자료 확정, 금지 표현 출력 필터, 문구표 공유.
